# Rulesets

A ruleset is the verified, versioned snapshot of game data that the solver is allowed to read: formula ASTs and tables for every mechanic, the equipment catalog, food and potion state machines, and the review decisions those snapshots were regenerated from. There is one ruleset, `osrs-f2p-v1`, for Old School RuneScape free-to-play PvP on standard worlds. Everything in it traces to a pinned OSRS Wiki revision in [`research/authoritative`](../research/authoritative) (see [`docs/data-provenance.md`](../docs/data-provenance.md)); the Rust pipeline reads only `mechanics.json` and `items.json`, while the Python package loads and validates the whole directory. Wiki-derived data in these files is licensed CC BY-NC-SA 3.0 (see [`research/README.md`](../research/README.md)).

## Files in `osrs-f2p-v1`

| File | What it holds | Read by | Regenerated by |
| --- | --- | --- | --- |
| `manifest.json` | Ruleset identity, environment, path to the source archive, required mechanics. | Python `load_ruleset` (the Rust binary does not read it) | Hand-maintained |
| `mechanics.json` | 53 mechanic records (all `verified` as of 2026-09-02) and the registry of 187 pinned sources. | Python and Rust | Mechanics hand-entered with tests; `add-items` appends sources |
| `items.json` | 150 verified equipment records (44 weapons, 18 two-handed, 6 ammo, 18 head, 4 neck, 22 body, 19 legs, 3 hands, 16 shields; 48 items carry a Defence requirement). | Python and Rust | `rebuild-items`, `add-items` |
| `item-verification.json` | One review decision per item. | `rebuild-items` | Hand-written or `add-items` |
| `consumables.json` | 7 foods and the Strength potion as state-transition graphs. | Python | `rebuild-consumables` |
| `consumable-verification.json` | Decisions for foods and potions. | `rebuild-consumables` | Hand-written |
| `food-scope.json` | Which consumables the search optimises, which are dominance-pruned, blocked or excluded, with reasons and sources. | Python | Hand-written |

## `manifest.json`

| Field | Value in `osrs-f2p-v1` | Meaning |
| --- | --- | --- |
| `ruleset_id` | `osrs-f2p-1def-pvp-2026-09-01` | Identity printed in every report's reproducibility metadata. |
| `solver_version` | `0.1.0` | Solver version the snapshot was built for. |
| `data_snapshot_id` | `bootstrap-2026-09-01-v6` | Identity of the data snapshot. |
| `retrieval_timestamp` | `2026-09-01T13:11:37.039664Z` | When the snapshot was assembled. |
| `source_archive` | `../../research/authoritative` | Directory of raw source records, relative to the ruleset. |
| `environment.game` / `environment.mode` | `Old School RuneScape` / `Free-to-Play PvP` | Scope. |
| `environment.defence_level` | `1` | The Python loader rejects any other value; the Rust `account-frontier --defence-levels` flag searches other Defence levels without touching the manifest. |
| `environment.combat_level_minimum` / `_maximum` | `30` / `40` | Production search rejects combat levels outside this range. |
| `environment.inventory_slots` | `28` | Inventory capacity used by the race and kit stages. |
| `required_mechanics` | 21 ids, listed below | Every id must pass `MechanicRegistry.require` before a production run. |

Required mechanics: `combat_level`, `melee.effective_strength`, `melee.max_hit`, `melee.accuracy`, `tick.pipeline`, `death.simultaneous_ko`, `melee.damage_timing`, `ranged.projectile_timing`, `magic.projectile_timing`, `movement.resolution`, `weapon.switch`, `food.swordfish`, `food.anchovy_pizza`, `food.lobster`, `food.tuna`, `food.meat_pizza`, `food.pumpkin`, `food.easter_egg`, `potion.strength`, `potion.strength_reboost_application`, `prayer.pvp_protection`.

## `mechanics.json`

Two arrays. `sources` registers every pinned page: `source_id`, `url`, `revision`, `retrieved_at`, `content_sha256`. `mechanics` holds one record per mechanic:

| Field | Meaning |
| --- | --- |
| `mechanic_id` | Dotted id, e.g. `melee.max_hit`, `ranged.rapid_attack_cooldown`, `magic.f2p.spells`. |
| `status` | `verified` is the only status the solver will use; `experimental` records (from timing experiments) are rejected until a dated review promotes them. |
| `value` | A formula AST (`{"op": "floor", "args": [...]}` with ops `ref`, `const`, `add`, `sub`, `mul`, `div`, `floor`, `max`, `gt`, `if`), a table (spells, prayers, style bonuses), an impact-timing map (`impact_delay_by_distance`, `minimum_distance`, `maximum_distance`), or a scalar. |
| `formula_version` | Names the pinned revision(s) the value was read from, e.g. `osrs-wiki-combat-level-15305725`; the account frontier refuses any other `combat_level` version. |
| `source_ids` | Registered sources the value cites. |
| `test_ids` | Test functions that prove the evaluation matches the page floor by floor. |
| `conflicts` | Optional; any entry makes `require` raise `MechanicConflictError`. |

The 53 mechanics cover the combat level; melee, ranged and magic effective levels, rolls and max hits; accuracy; the successful-zero-to-one PvP rule; combat-style bonuses; rapid cooldown; the tick pipeline, simultaneous-KO priority, melee, ranged and magic impact timing, movement; weapon switching; F2P prayer boosts, protection, drain, conflicts and flicking; Strength potion boost, drink delay, decay and reboost; the seven foods; the experience threshold; and the F2P standard spellbook through Fire Blast plus Bind and Snare.

## `items.json`

A JSON array of equipment records, sorted by `item_id`:

| Field | Type | Meaning |
| --- | --- | --- |
| `item_id` | integer | Game item id. |
| `name` | string | Item name. |
| `slot` | string | `head`, `neck`, `body`, `legs`, `hands`, `weapon`, `2h`, `ammo`, `shield`. |
| `requirements` | object | Skill level gates, e.g. `{"attack": 30}` or `{"defence": 40, "attack": 40}`; parsed from the page, never hand-written. |
| `quest_requirements` | array of strings | Quest gates stated in the page lead (three items need `Dragon Slayer I`). |
| `bonuses` | object | The 14 equipment bonuses: `attack_stab`, `attack_slash`, `attack_crush`, `attack_magic`, `attack_ranged`, `defence_stab`, `defence_slash`, `defence_crush`, `defence_magic`, `defence_ranged`, `melee_strength`, `ranged_strength`, `magic_damage`, `prayer`. |
| `attack_speed` | integer or null | Weapon speed in ticks; null for non-weapons. |
| `attack_range` | integer or null | Base attack range in tiles. |
| `attack_styles` | array of strings | Verified style ids such as `accurate_slash`, `aggressive_crush`, `rapid_ranged`, `longrange_ranged`; empty for armour. |
| `two_handed` | boolean | Occupies the shield slot when worn. |
| `weapon_type` | string or null | `scimitar`, `warhammer`, `two_handed_sword`, `shortbow`, `longbow`, `staff`, and so on; used by dominance and the panel's weapon-type representatives. |
| `ammo_ids` | array of integers | Ammunition this weapon can fire. |
| `spell_ids` | array of strings | Spells the item supports (empty in the current catalog). |
| `mechanic_flags` | array of strings | Special mechanics that make an item strategically distinct; currently only `projectile`. |
| `availability_scope` | string | Always `f2p_standard_world` for a verified record. |
| `free_to_play`, `members`, `obtainable` | booleans | Legality gates. |
| `status` | string | `verified` (the Rust loader treats anything else as illegal). |
| `source_ids` | array of strings | Registered sources: the page itself plus every source cited in the decision's `evidence_by_gap`. |

An item is legal for an account when it is verified, F2P-scoped, sourced, obtainable, every requirement is met by the account's levels, and every quest requirement is in the completed-quest set (`--completed-quests` in Stage 2).

## `item-verification.json`

`{"items": [decision, …]}`. A decision carries the fields the parser cannot prove (`obtainable`, `availability_scope`, `quest_requirements`, `two_handed`, `weapon_type`, `attack_styles`, `ammo_ids`, `spell_ids`, `mechanic_flags`), the `requirements` it asserts (which must equal the parsed page), `source_file` (the archive file name), `evidence_by_gap` (a list of registered source ids for each of `obtainability`, `skill_requirements`, `quest_requirements`, `ammo_compatibility`, `special_mechanics`, `verified_attack_styles`), and an optional `notes` field for corrections.

## `consumables.json` and `consumable-verification.json`

Each consumable record has `consumable_id`, `name`, `kind` (`food` or `potion`), `item_ids` (or `item_id_by_doses` and `initial_state` for the potion), `availability_scope`, `status`, `source_ids` and `transitions`. A food transition (`whole`, or `full` then `half` for pizzas) records `healing`, `eat_delay_ticks`, `attack_delay_ticks` and `next_state`; a potion transition per dose records `drink_delay_ticks`, `attack_delay_ticks`, the `effect` (`strength_boost` via the `strength_potion.boost` formula), `next_state` and `next_item_id`. The decisions file mirrors this with `expected_name`, `expected_item_ids`, `source_file`, the transitions, and `evidence_by_gap` for `eat_delay_ticks`, `attack_delay_ticks`, `state_transition_order`, `obtainability` and `availability_scope`.

`food-scope.json` then declares the search scope: swordfish and anchovy pizza are optimised; easter egg, lobster, meat pizza, pumpkin and tuna are verified but dominance-pruned with the dominator and reason stated; jug of wine and kebab are observed but blocked until their side effects can be represented in fight state; shark is excluded as members-only. `catalog_complete` is `false`.

## Regenerating

```powershell
$env:PYTHONPATH = 'src'
python -m pure_solver rebuild-items rulesets/osrs-f2p-v1 rulesets/osrs-f2p-v1/item-verification.json
python -m pure_solver rebuild-consumables rulesets/osrs-f2p-v1 rulesets/osrs-f2p-v1/consumable-verification.json
python -m pure_solver inspect rulesets/osrs-f2p-v1
python -m pytest tests
```

`rebuild-items` re-parses every decision's archived page, refuses any decision whose evidence, requirements or scope do not check out, and writes `items.json` sorted by id; `rebuild-consumables` does the same for `consumables.json`. `inspect` validates the catalogs, the source archive and the required mechanics and prints the canonical hashes of the item, consumable and mechanics databases, which every report echoes. The regeneration tests in [`tests/`](../tests) assert that the committed files equal a fresh rebuild, so a hand edit to `items.json` or `consumables.json` fails the suite. To add items, use `add-items` (see [`docs/data-provenance.md`](../docs/data-provenance.md#adding-an-item)).
